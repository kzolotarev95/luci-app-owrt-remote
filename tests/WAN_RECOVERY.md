# Восстановление Xray после пропажи выбранного WAN (v121)

Сообщения `No selected WAN has a physical IPv4 default route`, ошибки
генерации конфигурации и `crash loop 6 crashes` описывают последовательность:
временно исчез маршрут на выбранном uplink, каждый запуск агента завершался,
а procd прекратил повторные попытки запуска Xray. Затем Heartbeat смог
восстановиться самостоятельно. Он делает HTTP-запрос, поэтому его успех
не подтверждает работу двух обратных соединений Xray для Админки и SSH.

В прежнем `wan_reconcile_xray` остановленный Xray игнорировался; при возврате
того же интерфейса также ничего не происходило. Это подтверждённый дефект
восстановления. Причину исчезновения исходного маршрута и фактическое
текущее состояние Xray на удалённом устройстве только эти логи не определяют.

## Исправление

- Перед генерацией JSON служебный процесс ожидает выбранный WAN с физическим
  IPv4 default route. Проверка каждые 5 секунд, одна запись о начале ожидания
  и одна о возвращении WAN. Конфигурация в ожидании не заменяется.
- Ошибки UUID, JSON или проверки Xray при доступном WAN не маскируются
  ожиданием сети: генерация по-прежнему завершается с настоящей ошибкой.
- Heartbeat не перезапускает всю службу, пока все выбранные WAN недоступны.
- После подготовки WAN проверяются процесс Xray и состояние procd. Если
  Xray отсутствует и его instance не работает, но служба включена и Heartbeat
  работает, повторно регистрируется только instance `xray` через `service add`.
  Работающий процесс запуска, который ожидает WAN или готовит Xray, не трогается.
- Живой Heartbeat и остальные instance не удаляются. При прежнем здоровом
  туннеле на том же интерфейсе перезапуск не запрашивается.
- Блокировка в RAM исключает одновременные запросы восстановления; PID
  завершившегося worker освобождается. Повторные запросы ограничены интервалом
  300 секунд, в том числе при ошибке ubus. Успешный ответ ubus означает принятие
  запроса запуска, а не доказанную доступность Админки.
- Явная остановка через панель (`enabled=0`) или остановка всей службы
  не отменяется автоматикой. Невыбранные интерфейсы не используются.
- Источники установки, настройки LAN, DNS, Podkop и логика WAN policy routing
  не меняются этим исправлением.

Формат `service add` и строковых параметров respawn сверялся с исходниками:

- https://github.com/openwrt/procd/blob/master/service/service.c
- https://github.com/openwrt/procd/blob/master/service/instance.c
- https://github.com/openwrt/openwrt/blob/openwrt-24.10/package/system/procd/files/procd.sh

## Установка и откат

Windows PowerShell 5.1, роутер пользователя:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "C:\Users\k.zolotarev95\Documents\openwrt overlay\vps\deploy-wan-recovery-fix.ps1" -Router "root@192.168.2.1" -Action Install
```

Скрипт обновляет агент и WAN helper парой, сохраняет первую копию в
`/root/owrt-remote-backup-before-wan-recovery-v121`, проверяет shell-синтаксис
и побайтовое совпадение. Затем перезагружает только работающий Heartbeat,
чтобы в RAM не остался прежний shell с уже загруженными функциями.
Туннель при исправном Xray не перезапускается. Остановленный Heartbeat
не запускается принудительно. Ошибка установки восстанавливает файлы
до текущей попытки. UCI и рабочий JSON скрипт установки не заменяет;
обычный запуск Xray выполняет штатную проверку и генерацию конфигурации.

Установка подтверждается `WAN_RECOVERY_ROUTER_Install_OK`, это подтверждение
установки кода. Проверка состояния:

```powershell
ssh root@192.168.2.1 'owrt-remote status; owrt-remote heartbeat-diagnostics; logread -e owrt-remote | tail -n 60'
```

Откат к коду до первого применения:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "C:\Users\k.zolotarev95\Documents\openwrt overlay\vps\deploy-wan-recovery-fix.ps1" -Router "root@192.168.2.1" -Action Rollback
```

Для роутера друга нужен его собственный доступный SSH-адрес, VPN или человек
в локальной сети. Через оборванные обратные SSH/HTTP-туннели установить код
невозможно. Если WAN уже вернулся, для разового восстановления на самом
роутере можно выполнить `/etc/init.d/owrt-remote restart`, затем проверить
`owrt-remote status`. Сам по себе этот перезапуск не устанавливает исправление.

## Локальная проверка

`test_wan_recovery.py` моделирует длительное отсутствие маршрута, возврат
того же интерфейса, остановленный Xray при работающем Heartbeat, начальную
подготовку, исправный туннель, ручную остановку, параллельные запросы,
оставшуюся блокировку, отказ ubus и настоящую ошибку генерации JSON.
Поддерживает `OWRT_RECOVERY_TEST_SHELL` для BusyBox ash.

`test_wan_recovery_deploy.py` проверяет установку, повторную установку,
сохранение первой резервной копии, откат, отсутствие копии, повреждённый
payload, отказ проверки и отказ перезапуска Heartbeat без реального SSH.

Дополнительно запускаются регрессии WAN failover, host policy, HTTP/HTTPS
авторизации и перенаправлений. Проверка BusyBox ash выполняется локальной
Windows-сборкой BusyBox; OpenWrt 24.10.3 и настоящий procd на устройстве
требуют проверки пользователем. Прямой WAN на удалённом устройстве не
отключать для искусственного теста без независимого канала доступа.
